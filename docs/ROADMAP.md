# 编剧卡片系统 · 功能扩展策划方案

- 版本：v1（2026-10-24）
- 适用对象：产品 / 开发 / 设计接手人
- 现状基线：v1.1.0，纯静态本地优先，15 拍 × 3 种结构，卡片 + 大纲 + 诊断 + 版本历史 + 导出 + 离线
- 相关文档：`docs/HANDOVER.md`（交接报告）、`docs/DOMAIN.md`（域名）

---

## 0. 先说判断

现在这套工具解决的是**“把结构摆出来”**：按节拍填卡、看覆盖、看情感曲线、导出大纲。它已经比通用看板更懂编剧，但离“每天都会打开的工作台”还差三层：

1. **写得不够顺**：没有大纲视图、没有标签/筛选、没有版本历史、没有快捷键体系；卡片一多就难找。
2. **懂得不够深**：只有节拍覆盖和情感曲线，没有角色、地点、因果链、A/B/C 线、剧集/季；诊断停留在“数量”层面。
3. **带不走/带不回来**：数据只在单浏览器，没有历史版本、没有分享、没有协作。

所以路线图不是“加更多按钮”，而是按 **写作流 → 故事工程 → AI → 协作 → 正文** 五层推进。每一层都要能独立成立，不做“半成品大杂烩”。

## 1. 目标与原则

### 1.1 目标用户（按优先级）

| 人群 | 场景 | 付费/传播潜力 |
| --- | --- | --- |
| 电影/剧集编剧 | 开写前搭结构、分场、检查节奏 | 高，口碑传播 |
| 短剧/竖屏团队 | 60–120 个卡点快速迭代 | 高，团队采购 |
| 编剧课/工作坊 | 节拍表教学、作业批改 | 中，拉新 |
| 制片/策划 | 看结构、提意见、审阅 | 中，协作入口 |

### 1.2 产品原则

1. **本地优先**：默认不上传；云能力必须是显式开关。
2. **结构先于正文**：不和 Final Draft 抢排版，先把“每一拍”想清楚。
3. **中文编剧工作流**：中式剧本格式、集数、短剧节奏，而不是翻译 Save the Cat。
4. **可带走**：JSON 永远是完整数据源，任何新功能都不能把数据锁死。
5. **AI 是副驾**：只给建议，不自动改稿；每个建议可拒绝、可追溯。
6. **轻**：打开 2 秒内能写第一张卡；不要求登录、配置、教程。

### 1.3 北极星指标

> **每周完成“结构闭环”的项目数**：关键节拍全填 + 至少导出过一次大纲的项目数。

辅助指标：

- 激活：首次访问 5 分钟内创建 ≥3 张卡的比例。
- 留存：7 日内再次打开的比例。
- 深度：诊断打开率、灵感箱使用率、版本恢复率。
- 价值：导出率、完成项目数、分享/协作邀请数。
- 质量：Lighthouse ≥ 95、崩溃/报错率 < 0.5%、PWA 安装率。

## 6. Phase 1：写作流（2–3 周 / 12–15 人日）

目标：让用户**一天里愿意打开三次**，而不是“项目开始时用一次”。

### 5.1 大纲视图（3 人日）

- 卡片板 / 大纲列表双视图切换，状态记忆。
- 大纲按“幕 → 节拍 → 卡片”线性展开，显示场景、冲突摘要、情感、状态。
- 支持拖拽排序、行内编辑标题/描述、折叠幕。
- 键盘：↑↓ 选卡，Enter 展开编辑，Tab 进下一拍。
- 与卡片板共享同一数据，切换无丢失。

**验收**：100 张卡的项目切换 < 200ms；大纲中改字，卡片板同步。

### 5.2 标签与自定义字段（3 人日）

- 卡片增加：标签（多选/自由输入）、颜色、时间（日/夜/黄昏）、内外景已有、POV 角色、预估页数。
- 自定义字段：项目级定义 3–5 个字段（文本/单选/数字），卡片可填。
- 标签用于筛选、着色、导出列。

**数据**：`card.tags: string[]`（已有空数组）、`card.timeOfDay`、`card.pageEstimate`、`card.fields: Record<string,string>`；`project.fieldDefs`。

**验收**：标签输入有自动补全；导出 CSV/Markdown 包含新字段。

### 5.3 高级筛选与保存视图（3 人日）

- 组合条件：幕、节拍、状态、标签、情感、角色、地点、有无冲突、关键词。
- 结果计数、清空、保存为“视图”（如“只看存疑”“只看女主”）。
- 搜索支持 `tag:`, `status:`, `loc:` 前缀语法。

**验收**：3 个条件组合筛选 < 100ms；视图刷新后保留。

### 5.4 版本历史（5 人日，Phase 1 的核心）

- 自动快照：每次结构性变更（新增/删除/移动/批量）后，若距上次 >2 分钟，写一条快照。
- 存储：IndexedDB（`cardwrite.versions`），压缩 JSON，单项目保留最近 50 条 + 每日 1 条（30 天）。
- 时间线 UI：时间、卡片数、变更摘要；预览只读；恢复为当前（恢复前再存一条）。
- 手动“命名版本”，可锁定不被清理。

**验收**：恢复后数据、撤销栈、导出均正确；50 张卡的项目快照 < 100KB。

> 这一项直接解决“本地数据单点”的最大焦虑，优先级高于任何 AI 功能。

### 5.5 快速捕捉（2 人日）

- 全局快捷键（PWA 内 `N` 已有；增加 `⌘⇧N` 从任意页面打开快速添加）。
- PWA Share Target：手机分享文本/链接 → 直接进灵感箱。
- 粘贴多行文本 → 按空行拆成多张灵感卡。

**验收**：Android/iOS 安装 PWA 后可从分享菜单进入；桌面快捷键不冲突。

### 5.6 导出增强（2 人日）

- 分页 PDF 模板：A4 / Letter，按节拍分页，表头重复。
- 飞书/Notion 友好的 Markdown（表格 + 折叠）。
- Fountain 场景列表（`INT. 地点 - 日` + 动作/对白占位）。
- 导出前预览与字段勾选。

**验收**：30 张卡导出 PDF ≤ 3 页；Fountain 可被 Highland/Beat 打开。

### 5.7 写作目标与统计（2 人日）

- 项目目标：总卡片数 / 关键节拍完成 / 截止日期。
- 每日记录：新增卡片、修改次数、连续写作天数。
- 周报：本周新增、完成节拍、情感曲线变化。

**验收**：目标进度在顶部可见但不打扰；周报可导出。

**Phase 1 完成后的状态**：打开即写、找得到、改得动、丢不了、带得走。

## 7. Phase 2：故事工程（3–4 周 / 20–25 人日）

目标：从“节拍表工具”变成“**只有这里才有的结构分析**”。

### 6.1 角色 / 地点资料库（Bible）（5 人日）

- 实体：角色（姓名、别名、年龄、身份、欲望、恐惧、弧光）、地点（名称、内外景、描述、关联场景）。
- 卡片通过 `characterIds` / `locationId` 引用实体，而不是纯文本。
- 角色卡：出场卡片数、首次/末次出场、情感走向、关系网（简单）。
- 地点卡：场景数、复用次数、日夜分布。
- 迁移：现有 `location.place` 文本保留，提供“一键识别为地点实体”。

**数据 v3**：`entities.characters[]`、`entities.locations[]`；`card.characterIds[]`、`card.locationId?`。

**验收**：改名角色，所有引用卡片同步；删除实体时提示引用数。

### 6.2 因果链 BUT / THEREFORE（4 人日）

- 卡片之间可连“因为 / 但是 / 所以”（South Park 方法）。
- 链视图：横向时间线 + 连接线；断链高亮（有卡片但无因果）。
- 诊断：连续 3 张“然后…然后…”提示；关键转折是否由前一拍导致。

**数据**：`card.links: [{ to: cardId, type: 'because'|'but'|'therefore' }]`。

**验收**：链视图 100 张卡不卡；删除卡片自动清理连接。

### 6.3 A/B/C 故事线与泳道（4 人日）

- 定义故事线（名称、颜色、类型：主线/A/B/C）。
- 卡片分配故事线；板视图按线着色/筛选；泳道视图 × 幕。
- 节奏诊断：某条线连续 8 拍不出现；B 故事是否在中点后消失。

**数据**：`storylines[]`、`card.storylineId`。

**验收**：泳道视图可切换；筛选与导出包含故事线。

### 6.4 一致性检查（3 人日）

规则示例：

- 角色死亡后仍有出场（需 `character.status`）。
- 地点未在首次出现前铺垫（可配置）。
- 时间线倒退（`dayIndex` 递减）。
- 同一场景/同一事件重复。
- 关键道具出现后消失。

输出：可点击跳转的问题列表，分为“阻断/提醒/建议”。

**验收**：规则可开关；误报率可接受（先做 5 条）。

### 6.5 自定义节拍表与模板（4 人日）

- 内置更多结构：救猫咪、兔狲、悬疑 8 步、短剧 3 幕 12 卡点、竖屏 60 秒、三幕剧。
- 自定义：增删幕/节拍、改推荐数量、写提示；保存为“我的模板”。
- 模板导入/导出（JSON），可分享。

**数据**：`project.structure` 覆盖默认 `STRUCTURES`。

**验收**：切换模板不丢卡（同 3.3 的映射逻辑）；模板导出可被他人导入。

### 6.6 剧集 / 季（5 人日）

- `series` → `episodes`；每集一个卡片板；季视图显示集数、关键节拍完成度、角色出场矩阵。
- 跨集弧光：角色/故事线在集间的推进。
- 导出整季大纲。

**数据**：`series: { title, episodes: [{ id, title, projectId }] }`，或独立 `cardwrite.series` 存储。

**验收**：新建季 → 3 集 → 每集独立编辑；季视图统计正确。

> Phase 2 的顺序建议：**6.5 模板 → 6.1 Bible → 6.3 故事线 → 6.2 因果链 → 6.4 一致性 → 6.6 剧集**。先让用户“用得上”，再上重分析。

## 8. Phase 3：AI 协作（4–6 周 / 20–30 人日）

定位：**结构医生 + 场景助手**，不是代写机器。

### 7.1 接入方式

- **BYO Key**（首选）：用户填 OpenAI / Anthropic / DeepSeek / MiniMax 兼容 endpoint + key，存 IndexedDB/本机，不上传服务器。
- **可选代理**：Cloudflare Worker 代理，隐藏 key、限流、计费；需要账号与付费，后期再做。
- 统一 `AIProvider` 接口：`chat(messages, {jsonSchema})`；默认模型可配。
- 成本可见：每次调用前显示预估 token/费用；可设上限。

### 7.2 六个能力（按价值排序）

| # | 能力 | 输入 | 输出 | 人日 |
| --- | --- | --- | --- | --- |
| 1 | 节拍建议 | 当前项目摘要 + 空白/薄弱节拍 | 3 个可选方向，每个含冲突/转折 | 4 |
| 2 | 冲突医生 | 单张卡的主人公/目标/障碍 | 指出“目标不具体/障碍不构成阻力”，给 2 个改写 | 3 |
| 3 | 场景扩写 | 卡片 + 角色 + 前情 | 300–500 字场景草稿（动作/对白） | 5 |
| 4 | 对白打磨 | 选中对白 | 3 版不同语气 | 3 |
| 5 | 覆盖报告 | 全项目 | 结构/节奏/人物/逻辑四段式报告 | 5 |
| 6 | 角色弧光 | 角色 + 出场卡片 | 弧光曲线与缺失节点 | 3 |

交互原则：

- 所有输出进入“建议侧栏”，用户**逐条采纳**，不自动写库。
- 采纳时记录来源（模型、时间、prompt 版本），可撤销。
- 不上传整部剧本，只传相关资料（项目摘要 + 选中卡片 + 角色小传），并在 UI 明示“将发送哪些内容”。

### 7.3 隐私与安全

- 首次使用 AI 必须二次确认“内容将离开浏览器”。
- Key 只存本机；导出 JSON 默认不含 Key。
- 提供“完全离线模式”开关，关闭所有网络请求。
- Prompt 注入防护：用户文本作为数据分隔，不作为指令。

### 7.4 不做

- 不自动生成整集/整部剧本。
- 不做“一键成片”。
- 不在用户不知情时上传。

**验收**：关闭 AI 时零网络请求；开启后每次调用有成本提示；采纳/拒绝可追溯。

## 9. Phase 4：协作与同步（6–8 周 / 30–40 人日）

先验证需求，再决定投入。三种形态，按成本从低到高：

### 8.1 只读分享（3 人日）

- 生成分享链接：项目 JSON 压缩 + 只读 viewer（可放 URL hash 或 Cloudflare KV）。
- 可选密码/过期时间；不暴露编辑能力。
- 适合发给导演/制片看结构。

### 8.2 评论与批注（5 人日）

- 卡片级评论、@角色、已解决状态。
- 本地评论（单人）→ 云端评论（多人）两阶段。
- 导出带批注的 PDF。

### 8.3 账号与云同步（15–20 人日）

- Cloudflare D1（项目 JSON）+ R2（附件）+ Magic Link 登录。
- 冲突策略：先做“最后写入 + 版本历史”，不做实时 CRDT。
- 端到端加密可作为高级选项（key 在客户端）。
- 离线优先：本地为主，联网后台同步，冲突可视化。

### 8.4 团队审阅（5 人日）

- 角色：owner / editor / viewer。
- 审阅模式：只读 + 评论 + 建议卡（不直接改）。
- 活动日志。

**验收**：断网编辑 → 联网合并不丢数据；分享链接无法越权编辑。

> 如果目标是“个人编剧工具”，Phase 4 可以长期不做；如果要做团队/短剧工业化，8.1 + 8.2 先上，8.3 慎重。

---

## 10. Phase 5：正文与工业化（8 周+）

- **Fountain 编辑器**：卡片一键生成场景，支持动作/对白/转场；双向同步。
- **修订颜色**：蓝/粉/黄/绿/金/白，按稿次。
- **页数/时长估算**：中文字数 → 页数 → 分钟；按剧集类型校准。
- **拍摄分解**：场景、角色、道具、日夜、页数导出 CSV。
- **互操作**：Final Draft (.fdx) 导入/导出、PDF 中式格式。

这一层是“从结构工具变成写剧本工具”，投入大、竞争激烈，建议在前四层验证留存后再做。

## 11. 数据模型演进

### v3（Phase 1–2）

```json
{
  "schema": 3,
  "project": {
    "id": "uuid",
    "title": "…",
    "type": "tv-hour",
    "createdAt": "…",
```

## 12. 技术架构演进

| 层 | 现在 | 建议 |
| --- | --- | --- |
| 构建 | 无 | Vite（多页/单页均可），输出静态 |
| 语言 | 原生 JS | TypeScript（至少数据层） |
| 模块 | 单 IIFE | `data/` `ui/` `export/` `ai/` `sync/` |
| 状态 | 全局对象 + 快照 | 轻量 store（订阅 + reducer），保持快照撤销 |
| 存储 | localStorage | IndexedDB（项目 + 版本 + 实体），localStorage 只存偏好 |
| 测试 | 无 | Vitest + Playwright |
| CI/CD | 手动 | GitHub Actions：测试 → Pages → CF Pages |
| AI | 无 | Provider 接口 + BYO key + 可选 Worker 代理 |
| 同步 | 无 | Adapter 接口，先文件/云盘，后 D1 |

关键：**先抽 adapter，再换实现**。不要让 IndexedDB/云同步的细节渗进 UI。

## 13. 指标与验证

### 上线前（每个 Phase）

- 可用性：关键路径无报错；Lighthouse ≥ 95。
- 数据：迁移 100% 通过；旧 JSON 可导入。
- 性能：500 张卡渲染 < 300ms；筛选 < 100ms。
- 可访问性：axe 0 违规。

### 上线后

- 激活：首访 5 分钟内 ≥3 张卡。
- 留存：7 日回访 ≥ 30%（个人工具基线）。
- 深度：诊断打开率 ≥ 40%；版本恢复成功率 100%。
- 价值：导出率 ≥ 50%；完成关键节拍的项目 ≥ 20%。
- AI：建议采纳率 ≥ 25%；单次成本 ≤ ¥0.5。

### 验证方法

- 5 名编剧可用性测试（每人 30 分钟，任务：搭一集结构）。
- 埋点默认关闭；用本地匿名计数 + 用户主动反馈，或只在获得同意后上报。
- 访谈重点：哪一步最烦？为什么不用第二次？

## 14. 不做什么

- 不做完整剧本排版（Final Draft 替代）。
- 不做通用项目管理/看板。
- 不做自动生成整部剧本。
- 不做强制登录/强制云同步。
- 不做复杂的团队权限（在 Phase 4 验证前）。
- 不为了 AI 而 AI：没有明确输入/输出/验收的能力不做。

## 17. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 功能膨胀，变成“大而全” | 失去轻量优势 | 每期只做一个主题；新功能必须有“删除什么” |
